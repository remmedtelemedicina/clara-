🧩 Os 5 padrões que se repetem nos bugs

A maioria dos bugs abaixo vem de 5 problemas estruturais. Corrigir a raiz resolve vários bugs de uma vez — não são erros isolados, são sintomas dos mesmos 5 buracos.

Padrão 1 — A Clara confirma ações antes de verificar se funcionaram

"Vou te mostrar os horários" (e não mostra). "Seu pagamento foi gerado" (sem enviar o link). A IA narra sucesso que não verificou — perda direta de venda (N5). Regra: a IA nunca confirma sucesso antes da tool retornar o dado concreto.

Padrão 2 — Rígido demais com linguagem natural

Brasileiro não responde "SIM" — responde "pode mandar", "bora", "blz", "pode confirmar". Cada vez que a Clara não entende, ela trava ou joga para humano. Fricção invisível que custa conversão.

Padrão 3 — Erros de conteúdo médico (o mais caro de todos)

"Otoscópio para o olho" (instrumento de ouvido). Abscesso não bloqueado. Sugerir R$249 sem saber o remédio. Risco real ao paciente e à credibilidade. (Lado da Raíssa, no prompt — mas afeta a confiança em tudo.)

Padrão 4 — Falta controle operacional em tempo real

Hoje, se a Clara surta em produção, não há como desligá-la sem abrir o n8n. Falta volante: kill switch, bloqueio, comandos (N11, N12, N13).

Padrão 5 — Estado vaza entre sessões

A sessão velha contamina a nova — Agda recebeu checklist de trauma sem nunca ter falado disso (N7). Falta higiene de reset ao iniciar nova sessão.

N2 · Crítico
Mensagens duplicadas — paciente envia 2 msgs rápidas, Clara responde 2 vezes
Crítico
⚠️ O que está acontecendo
Quando o paciente envia duas mensagens em sequência rápida, a Evolution API dispara dois webhooks separados. O n8n processa os dois e a IA responde duas vezes — duplicando a conversa.

Confirmado nas conversas 4 e 6: endereço pedido em duplicata, e mensagem de número internacional disparando múltiplas vezes para o mesmo evento.
⚠️ Aconteceu de novo — 05/06/2026 (dois menus seguidos)
É o caso clássico: duas mensagens no mesmo segundo → dois webhooks → duas respostas. Veja a conversa real:
👤
Paciente
online
Olá, Bom dia!!10:06
Estou precisando marcar uma consulta 10:06 ✓✓
Clara[menu completo de opções 1 a 7]10:06
ClaraEntendi! 🧡 ...escolha uma das opções...10:06
❌ Paciente recebe o menu duas vezes no mesmo minuto — uma execução respondeu "Olá", a outra respondeu "marcar consulta".
🔧 Opção A — Debounce simples (recomendada)
1. Quando chega mensagem: registrar timestamp no Supabase
   como "ultima_mensagem_recebida"

2. Aguardar 2–3 segundos antes de processar

3. Antes de chamar o agente IA, verificar:
   SE chegou outra mensagem do mesmo número nos últimos 3 seg:
     → Ignorar a anterior (processar só a mais recente)
     → OU concatenar e processar uma vez só
🔧 Opção B — Flag de processamento
1. Ao receber mensagem: processando = true
2. Se chegar nova mensagem enquanto processando = true:
   → Guardar na fila, processar após a primeira terminar
3. Ao finalizar resposta: processando = false

⚡ Obs: o debounce (opção A) também resolve parcialmente o N6
   (número internacional em loop), então resolve dois bugs de vez.
Implementar debounce antes do nó da IA no webhook de entrada

N4 · Alta prioridade
Follow-up cego — dispara para todo mundo, inclusive quem foi mandado para a UPA
Alta
⚠️ Problema central descoberto
A variável motivo_encerramento já está descrita no prompt da Clara com 8 valores possíveis — mas nenhuma etapa do prompt realmente grava esse valor. É só documentação flutuando no ar.

O follow-up está cego e dispara para todos. Caso real: paciente Agda foi bloqueada por abscesso (31/05) e recebeu dois follow-ups automáticos no dia seguinte — uma mensagem completamente inadequada para alguém que foi mandada à UPA.

🛑 Regra inegociável — recusa NUNCA dispara follow-up
Essa é a regra mais importante do follow-up, e vale para os dois tipos de recusa:
  • Recusa automática (a Clara recusa) → sinal de alarme, urgência, caso inadequado, gestante, criança, etc. → bloqueado_alarme ou atendimento_recusado → NÃO dispara
  • Recusa manual (a equipe/Raíssa recusa ou bloqueia o paciente na mão) → tem que setar motivo_encerramento = "atendimento_recusado" E adicionar à lista de bloqueados (ver N12) → NÃO dispara, nunca mais

⚠️ Hoje a recusa manual não marca nada — então o follow-up dispara mesmo depois da equipe ter recusado. O comando bloqueia (N12) precisa setar o motivo automaticamente para fechar esse buraco.
📝 Regra de linguagem nas mensagens de follow-up — nunca prometer atestado
As mensagens automáticas de follow-up nunca podem prometer resultado médico nem usar a palavra "atestado" como se fosse garantido. O atestado é decisão exclusiva do médico após a consulta. 
❌ NUNCA escrever:
   "seu atestado"
   "finalize seu agendamento para atestado"
   "você ainda não recebeu seu atestado"
   prometer data ou prazo para o atestado

✅ SEMPRE escrever:
   "sua consulta" / "sua avaliação médica"
   "finalize seu agendamento de consulta médica"

Exemplo ERRADO:
   "Olá! Você ainda não finalizou seu agendamento
    para o atestado. Posso te ajudar?"

Exemplo CORRETO:
   "Olá! Você iniciou um agendamento de consulta médica
    com a REMMED mas não finalizou. Posso te ajudar a
    concluir? 🧡"

Vale para TODAS as mensagens automáticas, não só da opção 2.

O lock por número (solução abaixo) resolve os dois casos, porque serializa as mensagens: exec-A termina, exec-B começa — com estado já atualizado pela exec-A.
🔧 Solução — Lock por número de telefone
O debounce do N2 resolve parcialmente, mas N8 precisa de um
lock de sessão para garantir serialização mesmo com delay:

1. Ao receber mensagem: verificar se existe lock ativo para o número
   SE lock = true:
     → Enfileirar a mensagem (ou aguardar 3s e tentar de novo)
     → NÃO processar em paralelo

2. Ao iniciar processamento: setar lock = true no Supabase
   Campos sugeridos:
     processando          = true / false
     processando_desde    = timestamp  (para detectar lock travado)

3. Ao finalizar resposta: setar processando = false

4. Safety: se processando_desde > 30s → forçar processando = false
   (evita lock permanente em caso de crash no nó)

5. Ao detectar duas msgs em < 3s do mesmo número:
   → Concatenar as duas em uma só mensagem antes de processar
   → Ex: "1\nA consulta é por chat?" → processa tudo junto
   → Clara responde escolha do horário E a dúvida de uma vez
✅ Resultado esperado com o fix
Paciente envia "1" + "consulta é por chat?" → n8n junta as duas → Clara responde:
"Ótimo, horário 11:00 reservado! A consulta é por videochamada, mas também pode ser por chat dentro da plataforma 😊 Me diz seu CPF..."

Uma única execução, nenhum conflito de estado.
Lock por número (processando = true/false) + concatenar msgs simultâneas antes de processar

🔧 Como distinguir msg da equipe vs. msg do paciente (Evolution API)
No payload do webhook da Evolution API, o campo:
  message.key.fromMe = true   → mensagem enviada pelo número REMMED
  message.key.fromMe = false  → mensagem enviada pelo paciente

N10 · Crítico
Paciente retorna após handoff — Clara fica silenciosa para sempre
Crítico
⚠️ Caso real — 04/06/2026
👤
Paciente
visto por último: domingo
🗓️ Domingo — equipe assumiu manualmente → setor ficou travado em "AGUARDANDO_HUMANO"
⏩ Quinta-feira (4 dias depois)
Bom dia aí tem atendimento hoje?09:34 ✓✓
Olá, gostaria de falar sobre10:03 ✓✓
❌ Clara não respondeu nenhuma das duas — o setor seguia em "AGUARDANDO_HUMANO" do domingo, então a IA continuou silenciada. Paciente ficou horas sem atendimento.
⚠️ Por que acontece
O setor ficou travado em AGUARDANDO_HUMANO do domingo. Quando o paciente voltou 4 dias depois, o n8n viu esse setor e silenciou a IA — exatamente como deveria fazer durante um handoff ativo. Mas o handoff do domingo já tinha terminado. Não há nenhuma lógica que detecte "o handoff está ativo agora ou já era do passado?"
🔧 Solução — Auto-release por inatividade humana
Adicionar campo: ultima_atividade_humana = timestamp

1. Quando equipe assume → setar:
   - setor = "AGUARDANDO_HUMANO"
   - ultima_atividade_humana = now()

2. Quando equipe envia mensagem → atualizar:
   - ultima_atividade_humana = now()

3. No nó de entrada do webhook (antes de silenciar a IA),
   verificar se o handoff ainda está "ativo":

   SE setor = "AGUARDANDO_HUMANO" (handoff ativo)
   E (now() - ultima_atividade_humana) > 30 minutos
     → Auto-liberar: setor = "TRIAGEM_ATIVA"
     → Clara retoma o atendimento normalmente

   SE setor = "ENCERRADO"
   E (now() - ultimo_contato) > 4 horas
     → Auto-liberar: setor = "TRIAGEM_ATIVA"
     → Nova sessão começa do zero (ver N7)

4. Thresholds configuráveis e alinhados com o Controle Avançado:
   - HUMANO    → 30 min sem resposta da equipe → libera
   - ENCERRADO → 4 h após encerramento → libera (nova sessão)
   No caso real (equipe assumiu domingo, paciente voltou quinta),
   os 30 min já teriam liberado muito antes — paciente atendido.
✅ Integração com N9 (/liberar)
N9 e N10 se complementam:
— N9 (/liberar): equipe libera manualmente, na hora que quiser
— N10 (auto-release): sistema libera sozinho se equipe ficou inativa por X horas

Com os dois implementados, nenhum paciente fica no limbo indefinidamente.
Campo ultima_atividade_humana + verificar threshold de inatividade no nó de entrada

N11 · Nova feature
Kill Switch — desligar e ligar a Clara na hora via WhatsApp
Nova feature
⚠️ Por que precisa
Hoje, se a Clara começa a fazer algo errado (um bug em produção, uma resposta inadequada em loop, um problema na agenda), não há como desligá-la sem entrar no n8n. Em uma emergência isso custa tempo precioso e o paciente continua recebendo respostas erradas. O kill switch resolve: a Raíssa manda pausa do próprio WhatsApp e a Clara para na hora.
🔧 Tabela config_sistema no Supabase
CREATE TABLE config_sistema (
  chave         TEXT PRIMARY KEY,
  valor         TEXT,
  atualizado_em TIMESTAMPTZ DEFAULT NOW()
);

INSERT INTO config_sistema VALUES
  ('clara_ativa',    'true',          NOW()),
  ('owner_telefone', '5511XXXXXXXXX', NOW()),
  ('msg_fora_do_ar', 'Estamos com atendimento pausado. Retornamos em breve! 🧡', NOW());
🔧 Lógica no nó de entrada
1. Raíssa envia "pausa" do número dela (owner_telefone)
   → UPDATE config_sistema SET valor='false' WHERE chave='clara_ativa'
   → Responde: "🔴 Clara pausada. Nenhum paciente será atendido."

2. Raíssa envia "liga"
   → UPDATE config_sistema SET valor='true' WHERE chave='clara_ativa'
   → Responde: "✅ Clara ativa. Atendimento retomado!"

3. A cada mensagem de paciente, ANTES do agente IA:
   SE clara_ativa = false
     → responder msg_fora_do_ar (ou silêncio, a definir) → parar
     → NÃO processar com a IA
Tabela config_sistema + check clara_ativa no nó de entrada antes do agente IA

N12 · Nova feature
Lista de bloqueados — ignorar paciente + cortar follow-up na recusa manual
Nova feature
⚠️ Por que precisa — e a conexão com o follow-up
Alguns pacientes não devem ser atendidos pela Clara (casos difíceis, recusados manualmente, abusivos). Hoje não há como bloquear. E o mais importante: quando a Raíssa recusa um paciente na mão, o sistema não marca nada — então o follow-up automático ainda dispara para quem já foi recusado. O bloqueio precisa setar o motivo de encerramento automaticamente para fechar esse buraco (ver N4).
🔧 Tabela pacientes_bloqueados
CREATE TABLE pacientes_bloqueados (
  telefone     TEXT PRIMARY KEY,
  motivo       TEXT,
  bloqueado_em TIMESTAMPTZ DEFAULT NOW(),
  origem       TEXT   -- 'etiqueta_wpp', 'comando', 'manual'
);
🔧 Dois jeitos de bloquear
Método A — Etiqueta no WhatsApp Business (mais visual):
  1. Criar etiqueta "nao-atender" no WPP Business
  2. n8n verifica labels no payload da Evolution API a cada msg
  3. SE label "nao-atender" presente:
     → INSERT em pacientes_bloqueados (origem='etiqueta_wpp')
     → não responder → parar

Método B — Comando via WhatsApp:
  bloqueia 5511999...    → INSERT na lista
  desbloqueia 5511999... → DELETE da lista
🛑 Ligação obrigatória com o N4 (follow-up)
Ao bloquear um paciente (qualquer método), TAMBÉM setar na sessão:
   → motivo_encerramento = "atendimento_recusado"
   → equipe_assumiu = true

Assim o follow-up NUNCA dispara para quem foi recusado na mão.
Esta é exatamente a regra que a Raíssa pediu:
"quando eu recusar manualmente também não pode ter follow-up".
🔧 Verificação no nó de entrada
A cada mensagem, ANTES do agente IA:
  GET pacientes_bloqueados WHERE telefone = remetente
  SE encontrado → silêncio total → parar
  (não processa IA, não dispara follow-up, não responde nada)
Tabela pacientes_bloqueados + bloqueio seta motivo_encerramento = atendimento_recusado (corta follow-up)

N13 · Nova feature
Central de Comandos via WhatsApp (engloba o /liberar do N9)
Nova feature
📌 Substitui e amplia o N9
O N9 propunha só o comando /liberar. Esta central de comandos faz tudo de uma vez: liberar, pausar, bloquear, status. Implementar N13 já resolve o N9. Todos os comandos são enviados pela Raíssa do número dela (owner) e nunca chegam ao agente IA.
🔧 Tabela de comandos

liga                  → liga a Clara (N11)
atende 5511999...     → reseta setor p/ TRIAGEM_ATIVA, Clara retoma (N9/N10)
bloqueia 5511999...   → adiciona à lista + corta follow-up (N12)

🔧 Parser de comandos (nó Function, JavaScript)
const msg    = $input.item.json.message.toLowerCase().trim();
const sender = $input.item.json.sender;
const owner  = $('Config').item.json.owner_telefone;

// Só o owner pode mandar comando
if (sender !== owner) return [{ json: { is_command: false } }];

if (msg === 'pausa')  return [{ json: { cmd: 'pausa' } }];
if (msg === 'liga')   return [{ json: { cmd: 'liga' } }];
if (msg === 'status') return [{ json: { cmd: 'status' } }];

if (msg.startsWith('atende '))
  return [{ json: { cmd: 'atende', telefone: msg.replace('atende ','').trim() } }];
if (msg.startsWith('bloqueia '))
  return [{ json: { cmd: 'bloqueia', telefone: msg.replace('bloqueia ','').trim() } }];
if (msg.startsWith('desbloqueia '))
  return [{ json: { cmd: 'desbloqueia', telefone: msg.replace('desbloqueia ','').trim() } }];

return [{ json: { cmd: 'ajuda' } }];  // comando não reconhecido

N14 · Infraestrutura
Observabilidade — logs de todo evento relevante
Infra
⚠️ Por que precisa — hoje vocês estão cegos
Quando a Clara falha em silêncio (como no N5 — anuncia horários que nunca chegam), vocês só descobrem porque um paciente reclama ou a Raíssa lê a conversa. Não há como saber quantas vezes por dia o sistema falha, qual nó quebra mais, nem quanto tempo leva cada etapa. Sem visibilidade, cada bug vira uma investigação demorada às cegas.
🔧 O que logar
1. Toda tool call: nome, parâmetros, resposta (sucesso/erro),
   tempo de resposta em ms.
2. Toda mudança de setor: de qual → para qual, timestamp, motivo.
3. Todo handoff: quando foi p/ AGUARDANDO_HUMANO, quando liberou,
   quem liberou (comando ou auto-release).
4. Todo disparo de follow-up: número, motivo_encerramento,
   se foi enviado ou bloqueado e por quê.
5. Erros de execução: qualquer exceção, com o payload que causou.
🔧 Onde guardar
Tabela de logs no próprio Supabase já basta no início.
Campos mínimos:
  timestamp, tipo_evento, numero_paciente, dados (JSONB), resultado
⚡ Prioridade
Logar primeiro os erros de tool call (N5) e as mudanças de setor (N10) — são os mais críticos e os que mais ajudam a diagnosticar o resto.
Tabela de logs no Supabase + começar pelos erros de tool call e mudanças de setor

N16 · Infraestrutura
Regras duplicadas entre os 4 agentes — bomba-relógio
Infra
⚠️ Por que precisa
Vários itens dizem "adicionar no prompt de Triagem E Roteamento E Renovação E Agendamento". Quando uma regra mora em 4 lugares, um dia ela é atualizada em 3 e esquecida no 4º — e o mesmo paciente recebe respostas diferentes dependendo de qual agente responde.
🔧 Regras que hoje estão duplicadas entre agentes
- Reconhecimento de SIM/NÃO e variantes ("pode confirmar", "ok")
- Alarmes de segurança (lista de sinais que mandam p/ UPA)
- Regra de atestado (nunca prometer, sempre "avaliação médica")
- Especialidades (clínico geral + saúde mental + emagrecimento)
- Tom, emojis, formatação geral
💡 O que fazer
Criar um "bloco base" com as regras comuns, copiado de forma controlada para cada agente. Quando uma regra mudar, atualizar o bloco base e propagar — não editar cada prompt na mão. Pode ser um simples regras_compartilhadas.txt como fonte da verdade.
Identificar regras comuns + criar bloco base único propagado para os 4 agentes
