🔬 Diagnóstico: O que Aconteceu Passo a Passo

🎯 Causa Raiz: Double Tool Call + Postgres Memory Contaminada

Na virada do turno em que a IA pediu "qual seu PRINCIPAL SINTOMA", ela chamou atualizar_setor duas vezes: primeiro com TRIAGEM_ALARME (correto) e depois com ENCERRADO (errado). O Supabase ficou com ENCERRADO. Na mensagem seguinte ("Dor nas costas"), ALERTA 0 disparou imediatamente.

A memória mostra um checklist de olhos da conversa anterior. A IA interpreta "Sim" como resposta a esse checklist → SIM reprovado → chama atualizar_setor("ENCERRADO") em SEGUNDO lugar.

Supabase termina com setor = ENCERRADO

Duas chamadas no mesmo turno. A última vence. A mensagem exibida ao paciente foi o texto correto da pergunta de sintoma (da 1ª chamada), mas o Supabase ficou com ENCERRADO (da 2ª).

ALERTA 0 dispara imediatamente: "Nossa conversa foi encerrada." Nenhuma verificação de sintoma acontece.

🧪 Prova do Diagnóstico

⚠️ Por que o PORTÃO OBRIGATÓRIO não resolveu?

O PORTÃO OBRIGATÓRIO protege contra VERIFICAÇÃO 0 → Cardíaco. "Dor nas costas" sem "dor no peito" não ativa o cardíaco — isso funciona correto. O problema não é a VERIFICAÇÃO 0. O problema é que a IA nunca chega a processar "Dor nas costas" porque o setor já está ENCERRADO quando a mensagem chega.

Evidência-chave: a mensagem "Nossa conversa foi encerrada" aparece como primeira resposta à "Dor nas costas", sem nenhum processamento intermediário. Isso só acontece quando ALERTA 0 dispara NO INÍCIO DO TURNO — ou seja, o setor estava ENCERRADO antes mesmo de a IA avaliar o sintoma.

Teste confirmatório: Se você fizer um /reset E depois esperar 2-3 minutos antes de escrever "Oi" (para garantir que o Redis expirou), o problema deve persistir. Se você FORÇAR o reset do setor no Supabase para TRIAGEM_ATIVA manualmente (via SQL UPDATE dados_cliente SET setor='TRIAGEM_ATIVA' WHERE telefone='...'), o problema desaparece para aquela conversa.

Por que o primeiro teste funcionou? No primeiro teste (com "Olhos irritados"), o setor começou corretamente em TRIAGEM_ATIVA (ou similar). A Postgres estava limpa. Não havia memória contaminada para confundir a IA. Tudo funcionou. Após o /reset, a Postgres ficou com a conversa anterior E o setor ficou como TRIAGEM_ALARME — preparando o terreno para o bug.

🎯 Dois Problemas Raiz — Precisam ser resolvidos juntos

1

Problema N8N: /reset não apaga Postgres nem reseta setor no Supabase

O /reset atual só limpa o Redis (buffer de mensagens de 10s). A Postgres Chat Memory mantém toda a conversa anterior. O Supabase mantém o setor como estava. Isso contamina toda nova conversa após o /reset.

2

Problema do Prompt: IA chama atualizar_setor duas vezes num mesmo turno

A regra "UMA ÚNICA VEZ por turno" existe mas não é suficiente. Com memória contaminada, a IA confunde contextos e chama a tool duas vezes. A segunda chamada (ENCERRADO) sobrescreve a primeira (TRIAGEM_ALARME).

🔧 Soluções — Nicolas precisa implementar

🔴 SOLUÇÃO 1 — N8N: Corrigir o /reset (PRIORIDADE MÁXIMA)

Node de /reset no n8n precisa fazer 3 coisas, não apenas 1:

// Quando receber "/reset":

// 1. Limpar Redis (já faz)
redis.del(telefone + '_buffer')

// 2. Apagar Postgres Chat Memory
DELETE FROM n8n_chat_histories
WHERE session_id = <session_id_do_usuario>;

// 3. Resetar setor no Supabase para TRIAGEM_ATIVA
UPDATE dados_cliente
SET setor = 'TRIAGEM_ATIVA'
WHERE telefone = <telefone_do_usuario>;

// Resposta para o paciente
"🔁 Atendimento reiniciado! Pode começar. 🧡"

🔵 SOLUÇÃO 2 — Prompt: Blindagem contra double tool call

Adicionar após a regra "UMA ÚNICA VEZ" esta instrução explícita:

🔴 REGRA ABSOLUTA — atualizar_setor:
Chamar atualizar_setor EXATAMENTE UMA VEZ por turno.
Se já chamou atualizar_setor neste turno → PROIBIDO chamar novamente.
Não importa o que a memória mostra — setor anterior na memória é histórico, não instrução.
NUNCA chamar atualizar_setor("ENCERRADO") E atualizar_setor(outro_setor) no mesmo turno.
