Sistema de Follow-up da Clara — Implementação

Para Nicolas · Atualizado em 03/06/2026

📌 Contexto rápido

O follow-up é o disparo automático que manda mensagem para o paciente que parou no meio do atendimento ("Oi, vi que você começou um atendimento, posso te ajudar a continuar?"). Hoje ele dispara para todo mundo — inclusive para quem foi mandado para a UPA, para quem foi recusado por urgência e para quem a equipe já assumiu. Isso gera mensagens constrangedoras e fora de contexto.

A ideia é simples: o follow-up só deve disparar para quem realmente abandonou (parou no pagamento, no cadastro ou no meio da triagem). Para isso usamos uma variável chamada motivo_encerramento, que diz por que a conversa terminou.
A variável motivo_encerramento já está descrita no texto do prompt da Clara, com os 8 valores possíveis. MAS nenhuma etapa do prompt realmente grava esse valor — é só uma tabela de documentação que não conecta a nada. Resultado: o follow-up não tem como saber o motivo, então hoje ele está "cego" e dispara para todos.

Por isso a implementação tem duas frentes:
① Raíssa — fazer cada ponto de encerramento no prompt gravar o motivo (lado do texto)
② Nicolas — garantir que esse valor seja salvo no Supabase e lido pelo nó de follow-up (lado técnico)
🔍

Parte 1 — Como o motivo_encerramento deve funcionar

Tabela de referência: quais motivos disparam follow-up e quais não

Existem 8 motivos possíveis de encerramento. Apenas 3 deles devem disparar follow-up (os abandonos recuperáveis). Os outros 5 nunca devem disparar.
motivo_encerramentoQuando aconteceFollow-up?
pagamento_pendentePaciente recebeu o link mas não pagou✅ DISPARAR
cadastro_incompletoComeçou cadastro e não terminou✅ DISPARAR
abandonou_triagemIniciou triagem e parou de responder✅ DISPARAR
bloqueado_alarmeFoi mandado para UPA/SAMU (sinal de alarme)❌ NÃO
atendimento_recusadoRecusado por urgência / caso inadequado❌ NÃO
encerrado_pacientePaciente disse que não quer continuar❌ NÃO
pagamento_confirmadoJá pagou — atendimento seguiu❌ NÃO

Parte 2 — O que o Nicolas precisa fazer no n8n

Lado técnico: campo no Supabase + leitura no nó de follow-up

4 tarefas
1
Criar / confirmar o campo motivo_encerramento no Supabase
Precisa existir uma coluna motivo_encerramento na tabela de sessões/contexto (a mesma tabela onde fica o setor). É nela que o valor vai ser gravado e depois lido.
Tabela: (mesma do "setor" — ex: sessoes / contexto) Campo novo: motivo_encerramento (tipo: text, pode ser null) Se já existir, só confirmar que está acessível pelos nós de "Get a row" e "Update row".
Verificar se o campo existe; criar se não existir
2
Garantir que a tool atualizar_setor grave o motivo junto
Hoje a tool atualizar_setor recebe só o parâmetro setor. Para o follow-up funcionar, quando a Clara encerrar ela precisa conseguir gravar também o motivo. Duas formas possíveis — escolher a mais fácil de implementar:
atualizar_setor(setor, motivo_encerramento) → quando setor = "ENCERRADO", a Clara também envia o motivo → o nó Update row grava os dois campos de uma vez Vantagem: um só ponto de gravação, mais limpo.
Um nó Set/Function que olha o setor que a Clara mandou e deduz o motivo: setor = "ENCERRADO" + última ação foi bloqueio de alarme → "bloqueado_alarme" setor = "HUMANO" / "HUMANO_VOLUNTARIO" → "equipe_assumiu" setor = "AGENDANDO_*" / "AGUARDANDO_PAGAMENTO" → "pagamento_pendente" Vantagem: não precisa mexer no prompt nem na tool. Desvantagem: o setor "ENCERRADO" é usado para MUITos casos diferentes (UPA, recusa, paciente desistiu) — então sozinho ele NÃO distingue. Por isso a Opção A é mais segura.
Decidir Opção A ou B e implementar a gravação do motivo
3
Colocar a condição de disparo no nó de follow-up
No nó que dispara o follow-up automático, buscar o motivo_encerramento do número no Supabase e só seguir se ele estiver na lista dos que disparam.
DISPARAR follow-up SOMENTE SE: motivo_encerramento IN ( "pagamento_pendente", "cadastro_incompleto", "abandonou_triagem" ) NÃO DISPARAR SE: motivo_encerramento IN ( "bloqueado_alarme", "atendimento_recusado", "encerrado_paciente", "pagamento_confirmado", "equipe_assumiu" ) OU motivo_encerramento IS NULL ← por segurança, no caso de NULL não dispara
Se o motivo vier vazio/NULL, o padrão deve ser NÃO disparar. É melhor deixar de mandar um follow-up do que mandar para quem foi para a UPA. Enquanto a Parte de gravação (tarefa 2 + lado da Raíssa) não estiver 100%, isso evita disparos errados.
Adicionar IF no nó de follow-up lendo motivo_encerramento
4
Suprimir follow-up quando a equipe assumiu / pagamento manual
Independente do motivo, se a equipe humana assumiu a conversa ou já gerou cobrança manual, nenhum follow-up automático deve disparar. Isso conecta com o N1 e N3 do outro documento.
Quando a equipe assume (ex: comando /equipe no painel, ou setor = "HUMANO" / "AGUARDANDO_HUMANO"): → setar equipe_assumiu = true → motivo_encerramento = "equipe_assumiu" No nó de follow-up, além da condição da tarefa 3, checar: SE equipe_assumiu = true → NÃO disparar SE pagamento_status = "manual_gerado" → NÃO disparar SE pagamento_status = "confirmado" → NÃO disparar
Cruzar com flags equipe_assumiu / pagamento_status

Parte 4 — Como testar depois de implementar

Cenários para confirmar que o follow-up só dispara para quem deve

1. Simular paciente bloqueado por alarme (ex: "dor no peito") → motivo deve ficar "bloqueado_alarme" → follow-up NÃO pode disparar 2. Simular paciente que recebeu link e não pagou → motivo "pagamento_pendente" → follow-up DEVE disparar 3. Simular paciente que disse "não quero, obrigado" → motivo "encerrado_paciente" → follow-up NÃO pode disparar 4. Simular equipe assumindo a conversa → motivo "equipe_assumiu" / equipe_assumiu = true → follow-up NÃO pode disparar 5. Simular sessão sem motivo (NULL) → follow-up NÃO pode disparar (regra de segurança)
Ordem sugerida:
1️⃣ Criar o campo no Supabase (tarefa 1)
2️⃣ Colocar o IF de segurança no follow-up lendo o motivo — com NULL = não dispara (tarefa 3)
    → só isso já evita os disparos errados imediatamente
3️⃣ Decidir Opção A/B e gravar o motivo em cada encerramento (tarefa 2 + Raíssa)
4️⃣ Cruzar com equipe_assumiu / pagamento (tarefa 4)
5️⃣ Rodar os testes da Parte 4

Resumo: o follow-up é um sistema separado. Hoje ele dispara para todos porque o motivo nunca é gravado. Com o campo + a leitura no nó (com NULL = não disparar), o problema dos disparos constrangedores já é resolvido na hora.
