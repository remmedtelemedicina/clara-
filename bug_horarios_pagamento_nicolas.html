🔴 Bug Crítico — Análise Técnica

Horários e Link de Pagamento Não Chegam ao Paciente

REMMED Telemedicina · Clara Multi-Agent · Junho 2026

🚨 Impacto direto no faturamento

Toda vez que a Clara promete os horários ou o link de pagamento e vai ao silêncio, a consulta não é agendada e a receita é perdida. Esse bug foi identificado em pelo menos 3 conversas reais de pacientes (conversas 1, 2 e 7 da análise de junho/2026) e possivelmente afeta muitos outros casos não registrados.

🔍

O Problema — Explicação Simples

Para Raíssa entender e explicar pro Nicolas

O que acontece na prática
A Clara acorda apenas quando o paciente manda uma mensagem. Ela roda, faz uma coisa, manda uma resposta, e volta a dormir — esperando a próxima mensagem do paciente.

O problema: quando ela manda uma mensagem do tipo "Um momento, vou buscar os horários…" ou "Seu pagamento já foi gerado", isso é a resposta final do turno. Ela vai dormir. Os horários ou o link deveriam vir em seguida — mas nada acorda a Clara de novo, porque só o paciente pode fazer isso. E o paciente está esperando o link. Resultado: silêncio.
1. Paciente confirma o agendamento
2. Clara diz: "Um momento, vou buscar os horários disponíveis..."
3. Clara vai dormir ← isso é o fim do turno
4. Horários nunca chegam
5. Paciente espera em silêncio
1. Paciente escolhe PIX pela segunda vez
2. Clara diz: "Seu pagamento via PIX já foi gerado e seu atendimento está finalizado 😊"
3. Clara vai dormir — sem ter enviado o link
4. Paciente recebe mensagem de "sucesso" mas não sabe como pagar
5. Consulta nunca acontece
Por que a Clara faz isso?
O prompt não está proibindo mensagens de promessa. A Clara foi "treinada" (pelo prompt) a comunicar o que vai fazer — o que é educado em linguagem normal, mas tecnicamente impossível no sistema atual, porque ela não tem como agir depois de mandar a mensagem sem que o paciente envie algo primeiro.
Imagina que você contrata um funcionário que só pode trabalhar quando você fala com ele. Ele responde: "Já vou buscar os horários!" — e aí fica parado esperando você falar de novo. Você está esperando ele trazer os horários. Impasse.

Diagnóstico Técnico — Para o Nicolas

Baseado na análise do arquivo Fluxo_Mult_Agent_Clara_12.json

Arquitetura: modelo de 1 turno por mensagem
O workflow inteiro é disparado exclusivamente pelo Webhook EVO (nova mensagem WhatsApp). Não existe loop interno, auto-trigger ou timer. Cada chegada de mensagem = 1 execução do agente = 1 resposta = fim.
# Caminho completo (fluxo antigo — AGENDA_CONSULTA)
Webhook EVO → Entrada de Contato → ... → Get a row → Switch3
→ AGENDA_CONSULTA (agente roda aqui)
→ mensagem_paciente (Set: extrai $json.output)
→ If (output == "ROTEAR"?)
  └─ FALSE → Switch2 → Enviar texto1 ✅ paciente recebe
  └─ TRUE → Espera gerente Geral (wait node — pausa indefinida)

# O agente executa UMA vez e PARA. Não há re-trigger automático.
Por que a mensagem de promessa quebra o fluxo
Quando o agente produz um output como "Vou te mostrar os horários...":

1. $json.output = "Vou te mostrar os horários..."
2. O nó If avalia: é "ROTEAR"? → NÃO
3. Switch2 avalia: contém "equipe"? → NÃO
4. Enviar texto1 envia a promessa ao WhatsApp
5. Execução encerra — o workflow para completamente
6. A Clara volta a rodar só quando o paciente mandar outra mensagem
7. O paciente está esperando os horários — não manda nada — silêncio infinito
AGENDA_CONSULTA — agente LangChain com tools: listar-profissionais, listar-horarios, supabase_*, atualizar_setor, faq_remmed

GERAR_PAGAMENTO — agente LangChain com tools: gerar_cobranca, supabase_get_agendamento, atualizar_setor

mensagem_paciente — Set node: copia apenas $json.output

If — condição: $json.output == "ROTEAR"

Enviar texto1 — Evolution API, delay 4200ms, body: {{ $json.output }}
Dependência de 2 tools em sequência (listar-horarios)
Para buscar horários, o agente precisa fazer duas chamadas em cadeia no mesmo turno:
# Passo 1 — obrigatório antes do passo 2
listar-profissionais → extrai codigoProfissional

# Passo 2 — depende do resultado do passo 1
listar-horarios
  URL: .../listar-horarios/{{ $fromAI('codigoProfissional') }}
  dataInicial: {{ $fromAI('datasDisponiveis') }}
  dataFinal: {{ $fromAI('datasDisponiveis') }}

# Se o agente não chamar listar-profissionais primeiro,
# ele não tem codigoProfissional → listar-horarios falha silenciosamente
Se o agente pular o passo 1 ou a chamada falhar, ele não tem o código do profissional. O $fromAI() tenta gerar o valor, mas sem contexto real — podendo resultar em chamada com parâmetro errado ou vazio. Nenhum erro é exibido ao paciente — o agente simplesmente não consegue montar a lista.
Bug do link de pagamento (gerar_cobranca)
O agente GERAR_PAGAMENTO tem a tool gerar_cobranca vinculada como ai_tool. O fluxo correto seria:
# Fluxo correto (tudo no mesmo turno)
Chamar supabase_get_agendamento → extrair id_horario
Chamar gerar_cobranca com id_horario + forma_pagamento
Receber de volta: { charge_id: "xyz", link: "https://..." }
Output final: mensagem com o link embutido

# O que está acontecendo
Agente chama gerar_cobranca... OU
Agente NÃO chama e diz "Seu pagamento foi gerado" mesmo assim
Output final: "Seu pagamento via PIX já foi gerado 😊" — sem link
Enviar texto1 manda o texto sem link → paciente não sabe como pagar
O prompt do GERAR_PAGAMENTO já contém:
"🔴 NUNCA emitir a mensagem da Etapa 7 sem ter chamado gerar_cobranca com sucesso."
"🔴 NUNCA dizer ao paciente que 'o link foi gerado' se gerar_cobranca não foi chamada."

O agente está desobedecendo essas regras. A regra existe mas não tem força suficiente — precisa ser reformulada e reposicionada no prompt.
Ausência de tratamento de erro nas tools
Tool Retry Handler de erro vazio Handler de timeout
listar-horarios SIM (2s) NÃO NÃO
listar-profissionais SIM NÃO NÃO
gerar_cobranca NÃO NÃO NÃO
Quando qualquer uma dessas tools retorna vazio, null ou erro de API: o agente não sabe o que aconteceu e pode assumir sucesso ou travar silenciosamente. O paciente nunca é avisado.

Solução

Opção A (prompt) resolve imediatamente · Opção B (n8n) torna robusto

Opção A — Correção no Prompt (implementar agora)
Proibir mensagens-promessa. A Clara deve sempre buscar + formatar + enviar no mesmo turno, numa mensagem só. Nunca "vou buscar" / "um momento" / "já foi gerado" sem o resultado junto.
🔴🔴 REGRA ANTI-PROMESSA — LEIA ANTES DE TUDO 🔴🔴 Você roda UMA vez por mensagem do paciente. Quando você termina de responder, você para completamente e só volta a rodar quando o paciente mandar outra mensagem. Por isso, se você mandar uma mensagem do tipo "vou buscar" ou "um momento" ou "já foi gerado" sem o resultado junto, o paciente fica esperando para sempre — porque você não vai acordar sozinha para completar a ação. PROIBIDO — estas mensagens causam silêncio permanente: ❌ "Um momento, vou buscar os horários..." ❌ "Já vou te mostrar os horários disponíveis..." ❌ "Vou gerar seu link de pagamento..." ❌ "Seu pagamento já foi gerado" (sem o link na mesma mensagem) ❌ Qualquer promessa de ação futura sem o resultado junto OBRIGATÓRIO — tudo no mesmo turno, na mesma mensagem: ✅ Horários: chamar listar-profissionais → listar-horarios → responder com a LISTA COMPLETA na mesma mensagem. ✅ Pagamento: chamar gerar_cobranca → responder com o LINK na mesma mensagem. Só dizer "gerado" se o link estiver ali. SE A TOOL FALHAR OU RETORNAR VAZIO: → NÃO confirmar sucesso. NÃO inventar que funcionou. → Responder: "Tive um problema técnico agora. Pode tentar de novo em instantes ou falar com nossa equipe (opção 7)? 🧡" A mensagem da Clara sempre CONTÉM o resultado — nunca a promessa dele.
Opção B — Correções no n8n (tornar robusto)
Complementa a Opção A. Mesmo com o prompt correto, erros de API podem acontecer — o n8n precisa tratá-los.
  • 1
    Tratamento de erro no nó listar-horarios: Adicionar branch de erro. Se a resposta vier vazia ([]) ou com erro HTTP → retornar ao agente uma mensagem de erro estruturada como: { "erro": true, "mensagem": "Nenhum horário encontrado para essa data" } Assim o agente sabe que falhou e pode avisar o paciente corretamente. Crítico
  • 2
    Tratamento de erro no nó gerar_cobranca (Asaas): Se a API do Asaas falhar ou retornar sem link → NÃO deixar o agente assumir sucesso. Retornar: { "erro": true, "mensagem": "Falha ao gerar link de pagamento" } Crítico
  • 3
    Verificar se o link do Asaas está sendo incluído no output do agente: Confirmar que quando gerar_cobranca retorna com sucesso, o link (campo link ou invoiceUrl) está sendo passado de volta ao agente de forma que ele consiga incluir na mensagem. Se o agente não recebe o link, ele não pode enviá-lo. Alta
  • 4
    Consolidar AGENDA_CONSULTA e AGENDA_CONSULTA1: O fluxo novo (AGENDA_CONSULTA1 → Tratar Saída do Agente → ROTEAR ou Texto?) tem um problema: quando o output é texto normal, ele re-roteia pelo sistema de setores e nunca chega no "Enviar texto". Se esse fluxo está sendo usado, adicionar o "Enviar texto" antes do Get a row1. Alta
  • 5
    Adicionar timeout explícito no listar-horarios: Se a API da Amplimed demorar mais de 8s → retornar erro estruturado em vez de deixar o agente travado esperando. Média
  • 6
    Log de erros de tool call: Quando uma tool falha, registrar em log (Supabase ou console n8n) com: telefone do paciente, nome da tool, timestamp, erro recebido. Facilita diagnóstico futuro. Média
