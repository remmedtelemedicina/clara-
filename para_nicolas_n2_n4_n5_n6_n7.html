N2 · Crítico
Mensagens duplicadas — paciente envia 2 msgs rápidas, Clara responde 2 vezes
Crítico
⚠️ O que está acontecendo
Quando o paciente envia duas mensagens em sequência rápida, a Evolution API dispara dois webhooks separados. O n8n processa os dois e a IA responde duas vezes — duplicando a conversa.

Confirmado nas conversas 4 e 6: endereço pedido em duplicata, e mensagem de número internacional disparando múltiplas vezes para o mesmo evento.
🔧 Opção A — Debounce simples (recomendada)
1. Quando chega mensagem: registrar timestamp no Supabase
   como "ultima_mensagem_recebida"

2. Aguardar 2–3 segundos antes de processar

3. Antes de chamar o agente IA, verificar:
   SE chegou outra mensagem do mesmo número nos últimos 3 seg:
     → Ignorar a anterior (processar só a mais recente)
     → OU concatenar e processar uma vez só
🔧 Opção B — Flag de processamento
1. Ao receber mensagem: processando = true
2. Se chegar nova mensagem enquanto processando = true:
   → Guardar na fila, processar após a primeira terminar
3. Ao finalizar resposta: processando = false

⚡ Obs: o debounce (opção A) também resolve parcialmente o N6
   (número internacional em loop), então resolve dois bugs de vez.
Implementar debounce antes do nó da IA no webhook de entrada

   enviar mensagem de espera + tentar novamente.

Alta

A mensagem continuou disparando a cada mensagem enviada — tanto pela equipe quanto pelo paciente.
🔧 Solução técnica
1. A mensagem de número internacional deve disparar APENAS UMA VEZ
   — no primeiro contato do número estrangeiro.

2. Após disparar: setar internacional_notificado = true
   → Não disparar novamente para o mesmo número na sessão.

3. Quando a equipe assumir (setor = "AGUARDANDO_HUMANO"):
   → Suprimir completamente a mensagem internacional também
   → Toda automação não iniciada pelo humano deve ser silenciada.

4. Forma mais simples: mover verificação de número internacional
   para ANTES do nó de entrada geral.
   Se for internacional:
     → Disparar mensagem UMA vez
     → Setar setor = "AGUARDANDO_HUMANO" imediatamente
     → Não processar mais nada até equipe liberar
Setar AGUARDANDO_HUMANO após 1ª msg internacional + flag internacional_notificado

🔧 Solução técnica
1. Ao iniciar nova sessão (mensagem após >X horas de inatividade),
   resetar completamente o estado da sessão anterior no Supabase:
   - grupo_roteado       = null
   - checklist_atual     = null
   - estado_fluxo        = "MENU"
   - queixa_principal    = null
   - motivo_encerramento = null  (ou manter para follow-up — decidir)

2. Definir "nova sessão" como qualquer um de:
   → Inatividade > 4 horas  OU
   → Paciente envia saudação nova (oi, olá, bom dia, etc.)  OU
   → Conversa foi encerrada formalmente

3. Nunca usar variáveis de roteamento da sessão anterior para
   influenciar a nova triagem — cada sessão começa do zero.

4. Opcional: log de qual grupo foi atribuído e por quê,
   para facilitar diagnóstico quando acontecer de novo.
Reset completo das variáveis de sessão ao detectar nova sessão no Supabase

N8 · Crítico
Corrida de execuções — duas msgs simultâneas corrompem o estado da sessão
Crítico
⚠️ O que aconteceu — conversa analisada em 04/06/2026
O paciente escolheu o horário e no mesmo segundo fez uma pergunta ("a consulta é por chat?"). São duas mensagens separadas em milissegundos. A Evolution API disparou dois webhooks e o n8n abriu duas execuções paralelas. As duas leram o mesmo estado da sessão ao mesmo tempo e começaram a se atropelar:
  • Execução A leu estado = "escolha horário" → processou o "1" → avançou para "pedir CPF" → gravou novo estado
  • Execução B leu o estado velho (antes do CPF) → ficou bloqueada tentando responder a FAQ
  • CPF chegou e caiu no meio dessa briga → 5 minutos parado
  • Execução B "acordou" → pediu o CPF de novo (ignorou que já foi enviado) → "problema técnico"
⚠️ Sequência real da conversa
09:09  Clara: mostra horários disponíveis
09:10  Paciente: "1"                              ← escolheu
09:10  Paciente: "A consulta é por chat? Ou vídeo?" ← SIMULTÂNEO → dois webhooks
09:10  Clara: "preciso do seu CPF"                 ← execução A respondeu o "1"
09:11  Paciente: "40842469800"                     ← CPF enviado
       ⏳ 5 MINUTOS DE SILÊNCIO                    ← execuções em conflito
09:16  Clara: [responde chat/vídeo] + "preciso do CPF" ← pediu CPF DE NOVO ❌
09:16  Clara: "Tive um problema técnico..."         ← desistiu
🔧 Solução — Lock por número de telefone
O debounce do N2 resolve parcialmente, mas N8 precisa de um
lock de sessão para garantir serialização mesmo com delay:

1. Ao receber mensagem: verificar se existe lock ativo para o número
   SE lock = true:
     → Enfileirar a mensagem (ou aguardar 3s e tentar de novo)
     → NÃO processar em paralelo

2. Ao iniciar processamento: setar lock = true no Supabase
   Campos sugeridos:
     processando          = true / false
     processando_desde    = timestamp  (para detectar lock travado)

3. Ao finalizar resposta: setar processando = false

4. Safety: se processando_desde > 30s → forçar processando = false
   (evita lock permanente em caso de crash no nó)

5. Ao detectar duas msgs em < 3s do mesmo número:
   → Concatenar as duas em uma só mensagem antes de processar
   → Ex: "1\nA consulta é por chat?" → processa tudo junto
   → Clara responde escolha do horário E a dúvida de uma vez
✅ Resultado esperado com o fix
Paciente envia "1" + "consulta é por chat?" → n8n junta as duas → Clara responde:
"Ótimo, horário 11:00 reservado! A consulta é por videochamada, mas também pode ser por chat dentro da plataforma 😊 Me diz seu CPF..."

Uma única execução, nenhum conflito de estado.
Lock por número (processando = true/false) + concatenar msgs simultâneas antes de processar

N9 · Alta prioridade
Sem mecanismo para devolver paciente à IA após handoff humano
Nova feature
⚠️ Situação atual
Quando a equipe assume uma conversa, o setor vai para AGUARDANDO_HUMANO e a IA fica silenciosa. Não existe nenhuma forma de dizer ao sistema "ok, pode voltar a atender este paciente".

Para liberar hoje, a equipe precisaria acessar o Supabase diretamente e alterar o campo manualmente — completamente inviável no dia a dia.
🔧 Feature — Comando /liberar via WhatsApp
Fluxo proposto:

1. A equipe (Raíssa ou atendente) envia no WhatsApp do paciente:
   /liberar
   (pode ser: /liberar, /ia, /voltar, /clara — definir o mais intuitivo)

2. O webhook do n8n recebe a mensagem.
   ANTES de passar para o agente IA, verificar:
   SE a mensagem veio do número da equipe (fromMe = true na Evolution API)
   E a mensagem começa com "/"
     → NÃO processar como mensagem do paciente
     → Interpretar como comando interno

3. Comando /liberar:
   → Setar setor = "MENU" (ou "INICIO")
   → Setar equipe_assumiu = false
   → Limpar quaisquer variáveis de contexto da sessão anterior
   → (Opcional) Clara envia mensagem automática ao paciente:
     "Olá! Posso te ajudar com mais alguma coisa? 🧡"

4. Outros comandos úteis para o futuro:
   /status  → retorna o setor atual do paciente (debug)
   /reset   → limpa toda a sessão e começa do zero
   /info    → mostra dados da sessão atual
🔧 Como distinguir msg da equipe vs. msg do paciente (Evolution API)
No payload do webhook da Evolution API, o campo:
  message.key.fromMe = true   → mensagem enviada pelo número REMMED
  message.key.fromMe = false  → mensagem enviada pelo paciente

Já existe essa informação no webhook — só precisa checar
antes de passar para o nó da IA.
Checar fromMe no webhook + detectar comandos / antes de passar para o agente IA

N10 · Crítico
Paciente retorna após handoff — Clara fica silenciosa para sempre
Crítico
⚠️ Caso real — 04/06/2026
Domingo: paciente enviou mensagem → equipe assumiu manualmente
         → setor ficou = "AGUARDANDO_HUMANO"

Quinta (4 dias depois):
09:34  Paciente: "Bom dia aí tem atendimento hoje?"
10:03  Paciente: "Olá, gostaria de falar sobre"
14:00  REMMED: [mensagem em branco / silêncio]

Clara não respondeu nenhuma das duas mensagens.
Paciente ficou sem atendimento por horas.
⚠️ Por que acontece
O setor ficou travado em AGUARDANDO_HUMANO do domingo. Quando o paciente voltou 4 dias depois, o n8n viu esse setor e silenciou a IA — exatamente como deveria fazer durante um handoff ativo. Mas o handoff do domingo já tinha terminado. Não há nenhuma lógica que detecte "o handoff está ativo agora ou já era do passado?"
🔧 Solução — Auto-release por inatividade humana
Adicionar campo: ultima_atividade_humana = timestamp

1. Quando equipe assume → setar:
   - setor = "AGUARDANDO_HUMANO"
   - ultima_atividade_humana = now()

2. Quando equipe envia mensagem → atualizar:
   - ultima_atividade_humana = now()

3. No nó de entrada do webhook (antes de silenciar a IA),
   verificar se o handoff ainda está "ativo":

   SE setor = "AGUARDANDO_HUMANO"
   E (now() - ultima_atividade_humana) > 4 horas
     → Auto-liberar: setor = "MENU"
     → Clara retoma o atendimento normalmente

   SE setor = "AGUARDANDO_HUMANO"
   E ultima_atividade_humana recente (< 4h)
     → Manter silêncio (handoff ativo)

4. O threshold de 4h é configurável — pode ser 2h, 6h, 8h.
   Sugestão: 4h em horário comercial, 8h fora do horário.
✅ Integração com N9 (/liberar)
N9 e N10 se complementam:
— N9 (/liberar): equipe libera manualmente, na hora que quiser
— N10 (auto-release): sistema libera sozinho se equipe ficou inativa por X horas

Com os dois implementados, nenhum paciente fica no limbo indefinidamente.
Campo ultima_atividade_humana + verificar threshold de inatividade no nó de entrada
