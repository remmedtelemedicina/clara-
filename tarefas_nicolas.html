🔴 Crítico
N1 — IA continua respondendo após handoff confirmado para humano
O que aconteceu: paciente pediu "Falar com atendente". Clara confirmou a transferência. Mas quando o paciente enviou a próxima mensagem, a IA voltou a responder normalmente. Confirmado também na conversa 10: após Raíssa encerrar manualmente, Clara enviou mensagem genérica de "conversa encerrada" — quando deveria estar silenciosa.
Paciente: "Falar com atendente"
Clara: "Você será encaminhado para um atendente humano agora ✅"
Paciente: "Sim" (confirmou)
Clara: "Você já está falando comigo, que sou a atendente virtual..." ❌
Raíssa assumiu conversa e encerrou manualmente
Clara: Enviou mensagem automática de "conversa encerrada" ❌
→ Depois de handoff, qualquer automação deve estar silenciada
1. Quando Clara confirma o handoff para humano: → Setar variável: setor = "AGUARDANDO_HUMANO" 2. No início do nó principal da IA, adicionar condição: SE setor = "AGUARDANDO_HUMANO" → NÃO processar mensagem com agente IA → NÃO disparar follow-up automático → NÃO disparar mensagem de encerramento → Silêncio total da IA 3. Quando o humano liberar a conversa de volta para a IA: → Setar setor = "MENU" (ou estado inicial) → Pode ser feito com comando /liberar no painel interno Objetivo: qualquer nó automático deve verificar setor != "AGUARDANDO_HUMANO" antes de executar.
Condição no nó principal de entrada da IA + todos os nós de automação
🔴 Crítico
N2 — Mensagens duplicadas: paciente envia 2 msgs rápidas → Clara responde 2 vezes
O que acontece: quando o paciente envia duas mensagens em sequência rápida, a Evolution API dispara dois webhooks separados. O n8n processa cada um e a IA responde duas vezes. Confirmado nas conversas 4 e 6: endereço pedido em duplicata, e mensagem de número internacional disparando múltiplas vezes.
Opção A — Debounce simples (recomendada): 1. Quando chega uma mensagem, registrar o timestamp no Supabase como "ultima_mensagem_recebida" 2. Aguardar 2-3 segundos antes de processar 3. Antes de chamar o agente IA, verificar: SE chegou outra mensagem do mesmo número nos últimos 3 seg: → Ignorar a anterior (processar só a mais recente) → OU concatenar as mensagens e processar uma vez só Opção B — Flag de processamento: 1. Ao receber mensagem: processando = true 2. Se chegar nova mensagem enquanto processando = true: → Guardar na fila, processar após a primeira terminar 3. Ao finalizar resposta: processando = false Este debounce também resolve o problema da mensagem de número internacional disparando em loop (N6).
Implementar debounce antes do nó da IA no webhook de entrada

O que aconteceu: a equipe assumiu manualmente, gerou um link de Pix novo. Depois disso, o sistema de follow-up automático da Clara disparou o link antigo do Asaas. O paciente recebeu dois links de cobrança para a mesma consulta.
1. Quando a equipe intervém e gera cobrança manual: → Setar: pagamento_status = "manual_gerado" E/OU: equipe_assumiu = true 2. No nó de follow-up de pagamento, adicionar condição: SE pagamento_status = "manual_gerado" OU equipe_assumiu = true OU pagamento_status = "confirmado" → NÃO disparar o follow-up automático de cobrança 3. Comando interno: ao equipe enviar "/equipe" no painel → seta automaticamente equipe_assumiu = true → suprime todas as automações
Adicionar condição no nó de follow-up de pagamento

N4 — Sistema de follow-up inteligente com motivo_encerramento
Hoje o follow-up dispara para todo mundo — incluindo quem foi mandado para a UPA, quem foi recusado por urgência e quem a equipe já assumiu. Isso gera mensagens constrangedoras. A solução é uma variável motivo_encerramento que diz por que a conversa terminou — e o follow-up só dispara para os abandonos recuperáveis.

Depende do R3: Raíssa ajusta o prompt para gravar o motivo. Nicolas implementa a leitura no nó de follow-up.
A variável motivo_encerramento já está descrita no prompt da Clara com os 8 valores possíveis — mas nenhuma etapa do prompt realmente grava esse valor. É só documentação que não conecta a nada. O follow-up está "cego" e dispara para todos. Confirmado: paciente Agda foi bloqueada por abscesso (31/05) e recebeu dois follow-ups automáticos no dia seguinte.

O que aconteceu (conversa 1 e conversa 2):
— Conversa 1: Clara disse "Agora vou te mostrar os horários disponíveis com o médico" mas os horários nunca chegaram. A conversa terminou ali.
— Conversa 2: após paciente escolher PIX, sistema disse "Tive um problema ao gerar o link" → pediu para escolher de novo → paciente escolheu PIX de novo → Clara disse "Seu pagamento via PIX já foi gerado" mas nunca enviou o link.

Esses são os casos mais críticos de silêncio pós-confirmação: o fluxo quebra após a IA confirmar que vai fazer algo.
Clara: "Agora vou te mostrar os horários disponíveis..." → silêncio ❌
Possíveis causas: tool call falhou, timeout na API de agenda, resposta truncada
Paciente: escolhe PIX pela 2a vez
Clara: "Seu pagamento via PIX já foi gerado e seu atendimento está finalizado 😊"
→ Nunca enviou o link de pagamento ❌ → paciente não sabe como pagar
1. Adicionar tratamento de erro nos nós de tool call: - Busca de horários: se retornar vazio ou erro → responder "Tive um problema ao buscar os horários. Tente novamente ou fale com a equipe (opção 7)." - Geração de link Asaas: se retornar erro → NÃO confirmar que o pagamento foi gerado. Informar o erro ao paciente. 2. Verificar se a mensagem de sucesso do Asaas está: ① Enviando o link junto com a mensagem de confirmação ② Não assumindo sucesso antes de receber o link de volta 3. Adicionar log de erros de tool call para facilitar diagnóstico (quando a IA diz "vou enviar" mas não envia). 4. Timeout: se busca de horários demorar mais de 8s → enviar mensagem de espera e tentar novamente.
Verificar nós de busca de horários e geração de link Asaas — tratamento de erro

N6 — Mensagem de número internacional continua disparando após handoff humano
O que aconteceu (conversa 6): número estrangeiro (+58 Venezuela) → sistema enviou corretamente "Para atendimento internacional, nossa equipe entrará em contato em breve". Raíssa assumiu e começou a atender manualmente. Mas a mensagem automática continuou disparando após cada mensagem enviada pela equipe e pelo paciente — repetindo em loop.
Sistema: "Para atendimento internacional, nossa equipe entrará em contato em breve. 🧡"
Raíssa: "Boa noite! Tudo bem? Como posso te ajudar hoje?"
Sistema: "Para atendimento internacional..." ← dispara de novo
Paciente: "Atestado"
Sistema: "Para atendimento internacional..." ← dispara de novo ❌
1. A mensagem de número internacional deve disparar APENAS uma vez — no primeiro contato do número estrangeiro. 2. Após disparar, setar: internacional_notificado = true → Não disparar novamente para o mesmo número na mesma sessão. 3. Quando a equipe assumir (setor = "AGUARDANDO_HUMANO"): → Suprimir completamente a mensagem internacional também → Qualquer automação que não seja iniciada pelo humano deve ser silenciada. 4. Forma mais simples: mover a verificação de número internacional para ANTES do nó de entrada geral. Se for internacional: → Disparar mensagem uma vez → Setar setor = "AGUARDANDO_HUMANO" imediatamente → Não processar mais nada até equipe liberar
Setar AGUARDANDO_HUMANO após primeira msg internacional + suprimir repetição

N7 — Contexto de sessão anterior contamina nova sessão do mesmo paciente
O que aconteceu (conversa 9 — Agda, dia 2): paciente foi bloqueada no dia 31/05 por relatar "abscesso com pus". No dia seguinte (01/06), voltou, escolheu opção 1, disse que sintomas eram leves — mas o checklist que apareceu foi o de TRAUMA (dor após trauma, deformidade, dormência). Agda nunca mencionou sintoma musculoesquelético. O sistema parece ter "lembrado" algo da sessão anterior.
Agda (01/06): escolhe opção 1, confirma sintomas leves
Clara exibe checklist de TRAUMA sem nenhum contexto para isso

Hipótese: a variável de grupo/rota da sessão anterior não foi limpa e influenciou a sessão nova, ou houve cache de contexto entre conversas.
1. Ao iniciar nova sessão (mensagem após > X horas de inatividade), resetar completamente o estado da sessão anterior no Supabase: - grupo_roteado = null - checklist_atual = null - estado_fluxo = "MENU" - queixa_principal = null - motivo_encerramento = null (ou manter para follow-up) 2. Definir "nova sessão" como: → Inatividade > 4 horas OU → Paciente envia saudação nova (oi, olá, bom dia, etc.) OU → Conversa foi encerrada formalmente 3. Nunca usar variáveis de roteamento da sessão anterior para influenciar a nova triagem — cada sessão começa do zero. 4. Opcional: log de qual grupo foi atribuído e por quê, para facilitar diagnóstico quando acontecer de novo.
Garantir reset completo de estado ao iniciar nova sessão no Supabase
